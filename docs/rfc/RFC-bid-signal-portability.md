# RFC · BID 信号提取器可移植性（Signal Extraction Portability）

> **状态**：RFC-DRAFT（2026-10-19）· 待协议组议题化
> **缘起**：若琢 2026-10-19 暂缓 BID-A 取数，理由两条——① 本实例无 `bid_signal` 字段 ② 反对事后补造，建议「先定 schema，再在写入侧提取」。
> 该反馈暴露一个此前没被正视的事实：**`bid-signal.js` 一直是若兰家里的一段 lib，从未被当作协议看待。**
> **对应**：SPEC-MEM-0001 v2.0（现状实现）· BID v3.2 §6（采集层）
> **性质**：草案待议，勿引用为定论。

---

## 0. 一句话

> **一段只能在我们自己机器上跑的提取代码，不叫协议；只有当别的实例能装上、跑出可比较的结果，它才是。**

## 1. 问题陈述

### 1.1 现状

```
csb-memory/lib/core/bid-signal.js     ← 提取逻辑（若兰实例）
csb-memory/lib/core/memory.js#add     ← 两行钩子（写入时落字段）
```

- 代码在 CSB-Memory 仓里，随仓分发，但**没有任何规范文档定义它的行为**
- 词表、优先级、护栏规则写死在源文件注释里，**不是可引用的条款**
- 换一个实例（若琢的 DeepSeek Harness、言直的 Codex、启明的 pi-agent）装上后：
  - 跑出什么算「对」？没有判据
  - 结果能不能和我这边比？不知道
  - 词表升级了，对方还是旧版，怎么算？没有版本协商

### 1.2 实证触发（2026-10-19）

- 我们自己 4708 条记忆，带字段 **91 条（1.9%）**；一期上线后 4 天新增 170 条，带字段 **3 条（2%）**
- 质量脚本曾用 v1.0 裸词表判「漏网 36」，对齐 v2.0 后实际只有 **10**——**同一批数据两种口径差 3.6 倍**
- 结论：**没有条款约束的提取器，连自己家的读数都说不清，更不可能跨实例比**

## 2. 目标与非目标

### 目标

| # | 目标 |
|---|---|
| G1 | 把 `bid-signal.js` 的**行为**写成规范条款（输入、输出、判定规则、优先级、护栏） |
| G2 | 定义**一致性测试向量**（test vectors），任何实现跑过即视为「符合」 |
| G3 | 定义**版本协商**：词表升级时，跨实例如何判断可比性 |
| G4 | 让外部实例**可移植安装**：不依赖 csb-memory 其余部分，纯函数可单独取用 |

### 非目标

- ❌ 不规定实现语言（JS / Python / 任何语言都行，跑过向量即符合）
- ❌ 不规定记忆存储格式（正文字段怎么存是各家自己的事）
- ❌ 本期不做「自动安装/升级分发」（先把标准立住）
- ❌ 不改 verdict：**本 RFC 不改变任何现有指标口径**，只把已有行为写成可引用条款

## 3. 规范内容（草案）

### 3.1 输入

一条记忆条目，至少包含：

```
content : string   必填
title   : string   可选
tags    : string[] 可选
```

### 3.2 输出

```
null  或  { kind, peer, direction, state, origin }
```

| 字段 | 取值 | 规则 |
|---|---|---|
| `kind` | `promise` \| `correction` \| `decision` | **封闭枚举** |
| `peer` | 连接名 或 `null` | **宁空不猜**：必须处于关系位置才认 |
| `direction` | `in` \| `out` \| `null` | 仅 `correction` 有值，其余 `null` |
| `state` | `pending` | 写入时固定为 `pending`（四态回填属另一规范） |
| `origin` | `realtime` \| `backfill` | 写入路径 vs 存量补录 |

### 3.3 判定优先级（R12）

```
correction  >  promise  >  decision
```

一条文本命中多类时，取**最高优先级**的一类。

### 3.4 语境护栏（v2.0 核心，必须实现）

| 护栏 | 触发 | 行为 |
|---|---|---|
| **谈论护栏（meta）** | 信号词**前文子句**含「讨论/谈论/提到/关于/是否/判断/观测/统计/率/口径/定义/设计/词表/识别/抽取/正则/匹配/样本/举例/比如/例如/所谓」 | **不判** |
| **否定护栏（negation）** | 信号词**前文子句**含「无/非/未/不/没有/不存在/并无/不算/并非」 | **不判** |

**关键细节**：护栏只看**前文子句**（以 `。；;！!？?\n` 截断），不看后文。
原因：「更正一处口径」里的「口径」是宾语，不是元话语——看后文会误伤。

### 3.5 peer 判定（宁空不猜）

连接名必须处于**关系位置**之一才认：

```
① 与/和/同/对/向/给/跟/找 + 名字
② 名字 + 主动/表示/回复/反馈/指出/提出/确认/说
③ 调用方显式传入（最强）
```

都不满足 → `null`。

**反例（必须判 null）**：
> 「来源链条：…若琢 09-01 回帖承诺…」

这是在**引用**若琢的旧事，不是我与若琢之间的承诺。

## 4. 一致性测试向量（草案 · 待补全为正式素材）

> 任何实现跑过以下全部向量 = 符合本 RFC。素材文件 `test-vectors/bid-signal-v2.json`（待建）。

| # | 输入 | 期望 | 考察点 |
|---|---|---|---|
| V1 | `我承诺明天把 W-14 验完` | `promise` | 主体+承诺动作 |
| V2 | `TODO: 明天推 GitHub` | `promise` | TODO 分支 |
| V3 | `一澜决定采用方案 B` | `decision` | 决策动词+对象 |
| V4 | `一澜批准 SPEC-MEM-0002，直接开工` | `decision` | 批准类 |
| V5 | `我方更正：之前承诺的日期写错了` | `correction` | 优先级最高 |
| V6 | `评审通过，lint 修正 3 处` | **null** | 技术叙述不得误判为 correction |
| V7 | `签字结果：5×✅A 同意定稿，全员共识` | **null** | 评审叙述不得判 decision |
| V8 | `还要补一份 README` | `null`（已知漏报） | 口语承诺，接受漏 |
| V9 | `下次要记得问一澜` | `null`（已知漏报） | 口语承诺，接受漏 |
| V10 | `来源链条：…若琢 09-01 回帖承诺…` | `peer=null` | 引用 ≠ 关系 |

**V8/V9 是已知漏报**，向量里明确标注「接受」——**不追求召回，优先精确率**。

## 5. 版本协商（G3）

```yaml
signal_spec: bid-signal
version: 2.0          # 语义版本
wordlist_hash: <sha256>   # 词表+护栏的规范文本摘要
```

- 跨实例比对时，**`version` 相同才可比**；不同版本必须各自标注
- 词表调整 → 升 minor；护栏规则改动 / 输出结构改动 → 升 major
- **不追溯重算**：旧条目保持原判，不给历史数据换标签（对齐「无锚不改判」）

## 6. 待决议（协议组议题）

| 编号 | 议题 | 选项 |
|---|---|---|
| P-1 | 本 RFC 是否立项为正式规范（如 SPEC-MEM-0003） | A 立项 · B 只作指引文档 · C 不做 |
| P-2 | 测试向量由谁维护 | A 协议组统一维护 · B 各实现自带 |
| P-3 | 是否需要多语言参考实现 | A 只给 JS · B 加 Python · C 不限 |
| P-4 | 版本不匹配时跨实例数据怎么处理 | A 拒绝合并 · B 合并但标注 · C 换算 |
| P-5 | 漏报（V8/V9 类）是否要求召回下限 | A 不设（精确优先）· B 设一个宽松下限 |
| P-6 | `peer` 表（KNOWN_PEERS）是否进规范正文 | A 进（封闭清单）· B 出（可扩展，实现自维护） |
